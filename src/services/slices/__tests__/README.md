# Unit-тесты (Jest)

Документация по unit-тестам: что проверяется, как запускать, разбор тестов.

---

## Что тестируется

Редьюсеры Redux-слайсов:

- **`constructorSlice`** — добавление булки и начинок, удаление, перемещение, очистка, реакция на успешный заказ.
- **`ingredientsSlice`** — загрузка списка ингредиентов: состояния `pending`, `fulfilled`, `rejected`.

Тестируются **чистые редьюсеры** — без DOM и без сети. Редьюсер получает состояние и экшен, возвращает новое состояние.

## Запуск

```bash

npx jest --coverage   # + отчёт о покрытии
```

```
coverage/lcov-report/index.html
```

Папка `coverage/` — генерируемый артефакт, находится в `.gitignore`.

---

## Принцип проверок: «до → действие → после»

Редьюсер — чистая функция, поэтому у каждого теста три части:

1. **Состояние до** — исходный `stateBefore`.
2. **Действие** — вызов `constructorReducer(stateBefore, action)`.
3. **Состояние после** — проверки результата `stateAfter`.

Это соответствует принципу E2E-тестов (см. `tests/README.md`): сначала фиксируем исходное состояние, потом действие, потом результат. Только здесь «действие» — не клик, а вызов редьюсера с экшеном.

Отдельно проверяется, что редьюсер **не мутирует** входной `stateBefore` (например, в тесте `fulfilled` у `ingredients`).

## Тестовые данные

Все данные вынесены в `test-data.ts`, чтобы не дублировать их в каждом тесте:

- **`mockBun` / `mockMain` / `mockSauce`** — ингредиенты с типами `bun` / `main` / `sauce`.
- **`mockItems`** — массив из трёх ингредиентов (для ответа `fulfilled`).
- **`constructorBun` / `constructorMain` / `constructorSauce`** — те же ингредиенты, но уже с добавленным полем `id` (как в конструкторе).
- **`completedConstructor`** — собранный конструктор: булка + две начинки. Используется как состояние «до» для тестов удаления, перемещения и очистки.
- **`mockOrder`** — готовый заказ (номер `12345`), нужен для `createOrder.fulfilled`.

Картинки — инлайновые `data:image/svg+xml`: цветные прямоугольники вместо реальных файлов, чтобы тесты не зависели от изображений.

---

## Покрытие

```bash
npx jest --coverage
```

В отчёте информативнее метрика **% Branch**, чем **% Statements**: она показывает, какие ветки условий затронуты тестами (например, `pending` / `fulfilled` / `rejected` у асинхронных экшенов, ветка «булка уже есть» в `addIngredient`).

Сетевой слой (`burger-api.ts`) и работа с `document.cookie` (`cookie.ts`) в unit-тестах не покрываются — они проверяются на уровне E2E.

## Разбор тестов

### `constructorSlice.test.ts`

Проверяет редьюсер конструктора.

**Общий тест: `возвращает initialState при неизвестном экшене`**

- Редьюсер вызывается с `state = undefined` — так Redux задаёт начальное состояние при инициализации.
- Ожидается, что вернётся `initialState` (пустой конструктор).

---

#### `addIngredient`

**Тест: `сохраняет булку в state.bun`**

- Действие: `addIngredient(mockBun)`.
- После: `stateAfter.bun` содержит булку и новое поле `id`.
- `expect.any(String)` — тип проверяется, а конкретное значение нет: id генерируется внутри редьюсера.

**Тест: `заменяет старую булку на новую`**

- Состояние до: в конструкторе уже лежит булка (`constructorBun`).
- После: булка заменена, а `id` — **другой** (`not.toBe`), то есть создана новая запись, а не переиспользована старая.

**Тест: `добавляет начинку в конец списка`**

- После: в `ingredients` один элемент, он равен начинке с новым `id`.
- `bun` остаётся `null` — начинка не задевает булку.

**Тест: `добавляет несколько начинок в порядке добавления`**

- Действия: сначала `mockMain`, потом `mockSauce`.
- После: два элемента, порядок — как добавляли (`[main, sauce]`).

**Тест: `даёт разные id двум одинаковым ингредиентам`**

- Дважды добавляется **один и тот же** `mockMain`.
- После: обе записи имеют одинаковый `_id` (это один ингредиент), но **разные `id`** (это две разные позиции в конструкторе).

---

#### `removeIngredient`

**Тест: `удаляет начинку по id`**

- Состояние до: `completedConstructor` (две начинки).
- Действие: `removeIngredient(constructorMain.id)`.
- После: остаётся одна начинка — соус.

**Тест: `не меняет состояние при неизвестном id`**

- Действие: удаление с несуществующим `id`.
- После: состояние **равно** исходному (`toEqual(stateBefore)`), обе начинки на месте.

---

#### `moveIngredient`

**Тест: `меняет порядок начинок местами (0 -> 1)`**

- До: `[main, sauce]`.
- Действие: перемещение с индекса `0` на `1`.
- После: `[sauce, main]`.

**Тест: `меняет порядок начинок наоборот (1 -> 0)`**

- До: `[main, sauce]`.
- Действие: перемещение с индекса `1` на `0`.
- После: `[sauce, main]` — тот же результат, обратное направление.

---

#### `clearConstructor`

**Тест: `полностью очищает конструктор`**

- До: `completedConstructor` (булка + две начинки).
- Действие: `clearConstructor()`.
- После: состояние равно `initialState`, `bun = null`, `ingredients` пуст.

---

#### `createOrder`

**Тест: `fulfilled: очищает конструктор после успешного заказа`**

- До: `completedConstructor`.
- Действие: `createOrder.fulfilled(...)` — успешное завершение асинхронного экшена. Это `extraReducers`, но эффект проверяется в `constructorSlice`.
- После: конструктор пуст (`initialState`). Так заказ и очистка конструктора связаны одним экшеном.

---

### `ingredientsSlice.test.ts`

Проверяет редьюсер загрузки ингредиентов.

**Общий тест: `возвращает initialState при неизвестном экшене`**

- Те же принципы, что и в конструкторе: `undefined` + `UNKNOWN` → `initialState`.

---

#### `fetchIngredients`

**Тест: `pending: включает isLoading и сбрасывает error`**

- До: состояние с прошлой ошибкой (`error: { message: 'Старая ошибка' }`).
- Действие: `fetchIngredients.pending(...)` — запрос начался.
- После: `isLoading = true`, `error = null` (старая ошибка стёрта).

**Тест: `fulfilled: выключает isLoading и сохраняет ингредиенты`**

- До: `isLoading = true`.
- Действие: `fetchIngredients.fulfilled(mockItems, ...)` — данные пришли.
- После: состояние строго равно `{ items: mockItems, isLoading: false, error: null }`.
- Вторая проверка: `stateBefore.items` остался пустым — вход **не мутирован** (редьюсер вернул новое состояние, а не изменил старое).

**Тест: `rejected: сохраняет error, выключает isLoading, не трогает items`**

- До: сохранён один ингредиент (`mockBun`), `isLoading = true`.
- Действие: `fetchIngredients.rejected(error, ...)` — запрос упал.
- После: `items` не тронут, `isLoading = false`, `error` равен `action.error`.
- Проверяется, что `action.error.message` совпадает с текстом ошибки.
