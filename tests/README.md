# E2E-тесты (Playwright)

Документация по E2E-тестам страницы конструктора и создания заказа.

---

## Что тестируется

Флоу конструктора бургера:

- загрузка ингредиентов;
- пустое состояние конструктора;
- добавление ингредиентов;
- модальное окно ингредиента;
- создание заказа.
- закрытие модалки заказа.

Тесты идут против **реального приложения в браузере**, но **без реального бэкенда** — API подменяется (см. ниже).

## Запуск

```bash
npm run e2e                       # все E2E-тесты
npx playwright test -g "состав"   # тесты, где в названии есть "состав"
npx playwright test --ui          # интерактивный режим
npx playwright show-report        # последний HTML-отчёт
```

## Мокирование API (HAR)

E2E-тесты не обращаются к реальному бэкенду. Запросы к `/api/**` подменяются ответами из файла `hars/api.har`:

```ts
await page.routeFromHAR('./tests/hars/api.har', {
  url: '**/api/**', // перехватываются только запросы к API
  notFound: 'abort', // запроса нет в HAR — соединение обрывается
  update: false, // файл HAR не перезаписывается, только читается
});
```

Все ответы фиксированы в HAR, поэтому тесты не зависят от состояния бэкенда и работают без него. Параметр `notFound: 'abort'` гарантирует, что запрос, отсутствующий в HAR, не уйдёт в реальную сеть.

## Авторизация в тестах заказа

Helper `setupAuthorizedOrder` подготавливает залогиненного пользователя и собирает бургер.

Cookie `accessToken` устанавливается через `context.addCookies` с `url: baseURL` — приложение читает cookie со своего домена. Значение кодируется через `encodeURIComponent` — приложение декодирует его обратно.

Токен обновления кладётся в `localStorage` через `page.addInitScript`, то есть до загрузки страницы приложением.

После этого helper ожидает ответ `GET /api/auth/user` со статусом 200 и собирает бургер (булка, начинка, соус).

## Тестовые данные

Используется фиксированный набор ингредиентов:

- **Булка** — «Краторная булка N-200i», ID `bun-1`
- **Начинка** — «Биокотлета из марсианской Магнолии», ID `main-1`
- **Соус** — «Соус Spicy-X», ID `sauce-1`

Имена используются для поиска элементов в интерфейсе, ID — для проверки тела запроса.

Состав заказа в тестах: `['bun-1', 'main-1', 'sauce-1', 'bun-1']` — булка занимает первую и последнюю позиции.

## Принцип проверок: «до → действие → после»

Во всех тестах, где действие меняет состояние, проверяются **оба состояния**:

1. **До действия** — фиксируем исходное состояние (`toHaveCount(0)` или `toBeVisible()`).
2. **Действие** — клик, нажатие клавиши.
3. **После действия** — проверяем изменение.

Это гарантирует, что проверяемое изменение — **следствие действия**, а не случайность. Если бы элемент уже был в нужном состоянии до действия, тест без первой проверки прошёл бы ложно.

Для закрывающих сценариев принцип зеркальный: **есть → действие → нет**.

Принцип **не применяется**, там где действия нет:

- `отображает ингредиенты` — просто констатация загрузки;
- `конструктор пуст` — сам тест описывает начальное состояние;
- `отправляет состав заказа` — проверяется тело запроса, а не UI.

## Разбор тестов

Файл `constructor.pl.tsx` содержит 12 тестов, сгруппированных в `describe`-блоки.

### 1. Загрузка ингредиентов на странице конструктора

**Тест: `отображает ингредиенты после загрузки`**

Проверяет, что при открытии главной страницы три ингредиента (булка, начинка, соус) отрисовались и видны.

- Действия нет — тест констатирует загрузку данных, поэтому проверка «до» не нужна.
- Ищет имя каждого ингредиента через `getByText(...).first()`.
- `.first()` — потому что имя может встречаться в нескольких местах (в списке и в конструкторе).

### 2. Конструктор бургера в пустом состоянии

**Тест: `показывает заглушки и нулевую сумму при старте`**

Проверяет начальное состояние конструктора — до добавления ингредиентов.

- Это исходное состояние, действия нет — тест сам является проверкой «до».
- Заглушка «Выберите булки» видна **дважды** (верх и низ) — проверяется `toHaveCount(2)`.
- Заглушка «Выберите начинку» видна один раз.
- Элементов `constructor-bun-1` и `constructor-bun-2` **нет** — `toHaveCount(0)`.
- Сумма заказа содержит `0`.

### 3. Добавление ингредиентов в конструктор

**Тест: `добавляет булку в конструктор и обновляет сумму`**

Проверяет, что после добавления булки она появляется в конструкторе сверху и снизу, а сумма пересчитывается.

- **До действия:** булки в конструкторе нет (`toHaveCount(0)`).
- Клик по кнопке «Добавить» у булки (поиск: `li` с именем → кнопка внутри).
- **После действия:** булка отображается как `constructor-bun-1` (верх) и `constructor-bun-2` (низ).
- Текст содержит «(верх)» и «(низ)».
- Сумма = `2510` (1255 × 2, булка считается за две штуки).

**Тест: `добавляет начинку в конструктор и обновляет сумму`**

Проверяет, что начинка добавляется в отдельный контейнер и обновляет сумму.

- **До действия:** начинки в контейнере нет (`toHaveCount(0)`).
- Клик по «Добавить» у начинки.
- **После действия:** начинка отображается внутри `constructor-ingredients`.
- Сумма = `424` (стоимость одной начинки, булки в конструкторе нет).

### 4. Модальное окно ингредиента

**Тест: `открывается по клику и показывает данные выбранного ингредиента`**

Проверяет, что клик по ингредиенту открывает модалку с его данными.

- **До действия:** модалки нет (`toHaveCount(0)`).
- Клик по ссылке ингредиента меняет URL на `/ingredients/main-1`.
- **После действия:** появляется диалог (`role="dialog"`) с заголовком ингредиента.
- В модалке **нет** заголовка булки — открыт именно выбранный ингредиент.

**Тест: `закрывается по клику на крестик`**

Проверяет закрытие модалки через кнопку «Закрыть».

- **До действия:** модалка открыта (`toBeVisible()`).
- Клик по кнопке «Закрыть».
- **После действия:** модалка и оверлей исчезают (`toHaveCount(0)`), URL возвращается к `/`.

**Тест: `закрывается по клику на оверлей`**

Проверяет закрытие модалки кликом по затемнённому фону.

- **До действия:** модалка открыта.
- Клик по углу оверлея (`{ x: 10, y: 10 }`), чтобы не попасть в саму модалку.
- **После действия:** модалка и оверлей исчезают, URL возвращается к `/`.

**Тест: `закрывается по Escape`**

Проверяет закрытие модалки клавишей Escape.

- **До действия:** модалка открыта.
- Сначала клик по заголовку — фокус переходит внутрь модалки.
- Нажатие Escape.
- **После действия:** модалка и оверлей исчезают, URL возвращается к `/`.

### 5. Создание заказа

Эти четыре теста используют helper `setupAuthorizedOrder` (авторизация + сборка бургера).

**Тест: `отправляет заказ с правильным составом ингредиентов`**

Проверяет тело POST-запроса на `/api/orders`.

- Проверяется тело запроса, а не UI, поэтому «до/после» по DOM не применяется.
- Ловушка `waitForRequest` регистрируется до клика по «Оформить заказ».
- Проверяются URL и метод запроса.
- Тело: `{ ingredients: ['bun-1', 'main-1', 'sauce-1', 'bun-1'] }` (булка занимает первую и последнюю позиции).

**Тест: `показывает модалку с верным номером заказа`**

Проверяет, что после оформления показывается модалка с номером из ответа.

- **До действия:** модалки нет (`toHaveCount(0)`).
- Клик по «Оформить заказ».
- **После действия:** появляется диалог, виден номер `123456` (из HAR-ответа), поиск с `exact: true`.

**Тест: `очищает конструктор после оформления`**

Проверяет, что после успешного заказа конструктор обнуляется.

- **До действия две проверки:** модалки нет (`toHaveCount(0)`) и бургер собран — верхняя булка видна (`constructor-bun-1`).
- Клик по «Оформить заказ».
- **После действия:** ожидается модалка с номером — сигнал, что заказ прошёл.
- Затем проверяется пустое состояние (те же условия, что в тесте №2): заглушки на месте, булок нет, сумма `0`.

**Тест: `закрывает модалку заказа и проверяет успешность закрытия`**

Проверяет, что модалку с номером заказа можно закрыть, и что после закрытия она действительно исчезает.

- **До действия:** модалки нет (toHaveCount(0)).
- Клик по «Оформить заказ».
- **После действия:** модалка открылась, номер 123456 виден.
- Клик по кнопке «Закрыть» (крестик в шапке модалки).
- После закрытия: модалка и оверлей исчезают (toHaveCount(0)).

Отличие от тестов модалки ингредиента: здесь не проверяется toHaveURL — модалка заказа не привязана к URL (закрывается через closeOrderModal в Redux, а не через navigate).
